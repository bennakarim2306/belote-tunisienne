# RCA — iOS instant native crash on first touch (Belote Tunisienne)

## Scope / what this is
- iOS EAS build **succeeded** (EAS build `2dc147c9-6dc1-439b-a67b-8fb86eafcfb8`, cloud build `9e18678d...`), uploaded to TestFlight OK. This is a **runtime** crash on-device, not a build/pipeline failure.
- Code snapshot built = deploy run `eb37e510-7dd1-4697-8d64-490a19a38a41`.

## Evidence limits (be honest)
- A **green iOS build stores only marker lines** — the detailed `pod install` / autolinking / New-Arch warnings / Info.plist/entitlements output is NOT retained, so points (1)(2)(4) of the request **cannot be confirmed from logs**.
- A native iOS crash **cannot be reproduced in the eph sandbox** (no Xcode/iOS, no device). So the conclusion below is an **evidence-based inference from source**, not a reproduced/verified fix. Definitive confirmation needs a **symbolicated device crash log** from the iPhone (Settings → Privacy → Analytics & Improvements → Analytics Data, or Xcode → Devices → View Device Logs).

## Confirmed from source (snapshot inspected in eph pod)
- Versions are SDK-54 canonical: expo 54.0.35, RN 0.81.5, react 19.1.0, react-native-screens 4.16.0, reanimated 4.1.1 + react-native-worklets 0.5.1 (correctly paired for Reanimated 4), react-native-google-mobile-ads 16.0.3. `newArchEnabled: true`.
- `app.json` has a **DUPLICATE `expo-build-properties` plugin**: `["expo-build-properties", {android:{proguard...}}]` AND a later bare `"expo-build-properties"`. **No iOS build properties are configured anywhere** (no `ios.deploymentTarget`, no `ios.useFrameworks`).
- Home screen is under `app/(tabs)/`; `app/(tabs)/_layout.tsx` wraps everything in `NotificationsProvider > AdsProvider`, and renders an AdMob `<BannerAd>` in the tab bar. `AdsProvider` runs on mount: `AdsConsent.gatherConsent()` then `mod.default().initialize()` then `preloadInterstitial()`.
- The two crashing actions both **create a new native surface on iOS**: opening `<Modal>` (RCTModalHostView → a new RN surface/UIWindow) and `router.push` (react-native-screens → a new RNSScreen view controller). Home itself renders fine (banner mounts collapsed; SDK init apparently doesn’t crash at mount).

## Most likely root cause (ranked)
**Primary: a New-Architecture (Fabric) native-view incompatibility in the AdMob / ad-view native layer (react-native-google-mobile-ads 16.0.3), surfacing the moment a *new* native surface is instantiated.** Android (also New Arch) runs the identical JS fine, so the differentiator is the iOS native pod layer. The app survives home render (existing root surface) but crashes when a *fresh* iOS surface is created (Modal present / screen push), which re-triggers native component resolution. The AdMob stack is the most recently changed native surface (added `userTrackingUsageDescription` → pulls in ATT/UMP presentation; `iosAppId` set) and is the leading suspect for a Fabric view/registration or view-controller-presentation fault.

**Contributing / to rule out:**
- **Duplicate + empty `expo-build-properties`** means iOS build props were effectively defaulted. If the AdMob/UMP pods need a specific linkage (`useFrameworks: "static"`) or deployment target, it was never applied. This is a genuine config defect regardless and should be fixed.
- Sign in with Apple (`usesAppleSignIn:true` + expo-apple-authentication) — only relevant on the auth button, not Modal/other nav; lower likelihood but confirm the entitlement.

## Recommended fix / triage (fastest path to certainty)
1. **Pull the symbolicated iOS crash log from the device** — it will name the crashing framework/selector (GAD*/UMP vs RNScreens vs Reanimated) and end the guessing in one step.
2. **Fast isolation rebuild:** set `ADS_ENABLED = false` in `frontend/src/ads/config.ts` and rebuild iOS. If the crash disappears → it is the AdMob native layer; if it persists → move to react-native-screens/reanimated New-Arch interplay.
3. **Fix the duplicate plugin:** remove the bare `"expo-build-properties"` entry in `app.json` and consolidate into the single array entry; add an explicit `ios` block there (e.g. `deploymentTarget`, and `useFrameworks: "static"` if AdMob/UMP requires it).
4. If (2) implicates AdMob, confirm `GADApplicationIdentifier` is present in the built Info.plist and that the iOS app ID / unit IDs are valid, and verify react-native-google-mobile-ads 16.0.3 New-Arch support for the ad view components; consider pinning to a version with confirmed Fabric support or enabling the Fabric interop layer.
